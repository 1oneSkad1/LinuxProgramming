# 동일 형식의 트래픽 데이터를 반복 분석하는 리눅스 기반 병렬 처리 시스템

## 1. 프로젝트 개요

이 프로젝트는 동일한 형식으로 수집된 트래픽 데이터를 입력받아, 정해진 분석 작업을 정확하고 효율적으로 수행하는 C 기반 리눅스 프로그램을 개발하는 것을 목표로 합니다.

하루치 데이터의 분석 결과는 시스템의 동작을 확인하는 실험 사례로 활용합니다. 프로젝트의 중심은 새로운 날짜의 데이터를 입력하더라도 코드를 수정하지 않고 같은 절차로 분석할 수 있도록 입력, 작업 분배, 병렬 처리, 통계 병합, 결과 저장 과정을 구성하는 데 있습니다.

> 핵심 질문: 동일한 형식의 대용량 트래픽 데이터를 어떻게 반복 가능하고, 정확하며, 빠르게 처리할 수 있을까요?

## 2. 목표와 전제

### 목표

- 입력 디렉터리와 실행 옵션만 변경하여 다른 날짜의 데이터를 분석할 수 있도록 합니다.
- 데이터 해석, 분석 연산, 병렬 실행, 결과 출력을 모듈로 분리합니다.
- 단일 스레드 기준 구현과 병렬 구현의 결과가 일치하도록 합니다.
- 스레드 수에 따른 실행 시간과 처리량을 측정하여 병렬 처리의 효과와 한계를 설명합니다.
- 잘못된 입력이나 읽기 실패를 발견하고, 처리 결과와 함께 오류를 보고합니다.

### 전제

- 분석 대상 데이터의 파일 형식과 필드 의미는 동일합니다.
- 입력 파일은 수집이 끝난 상태이며 분석 도중 변경되지 않습니다.
- 타임스탬프, 출발지 IP, 목적지 IP, 패킷 길이를 해석할 수 있다고 가정합니다. 실제 필드 제공 여부와 길이의 의미는 데이터 확인 후 확정합니다.
- 한 번의 실행에서 지정한 디렉터리의 데이터를 분석하며, 하루치 데이터가 기본 실험 단위입니다.
- 구체적인 바이너리 구조, 헤더 길이, 바이트 순서, 레코드 경계는 실제 파일 명세와 제공 코드를 확인한 뒤 결정합니다.

## 3. 프로젝트 범위

### 필수 구현

| 영역 | 구현 내용 | 완료 기준 |
|---|---|---|
| 입력 관리 | 디렉터리에서 분석 대상 파일 목록 생성 | 동일 형식의 다른 데이터 경로를 입력하여 실행 가능 |
| 데이터 해석 | 파일 레코드를 공통 구조체로 변환 | 정상 레코드와 잘린 레코드 등을 구분 |
| 기준 분석기 | 단일 스레드 순차 처리 | 병렬 결과를 검증할 기준 결과 생성 |
| 병렬 실행기 | 고정 개수의 작업 스레드와 작업 큐 | 지정한 스레드 수로 파일 단위 작업 분배 |
| 통계 처리 | 스레드별 집계와 최종 병합 | 기준 분석기와 정수 통계 결과 일치 |
| 결과 출력 | 요약, 호스트별 통계, 시간대별 통계 저장 | 같은 열 구성을 갖는 CSV 생성 |
| 성능 측정 | 전체 실행 시간과 처리량 기록 | 스레드 수별 비교 실험 가능 |
| 오류 처리 | 입력·해석·출력 오류 보고 | 불완전한 실행을 정상 완료와 구분 |

### 선택 확장

- 다중 프로세스 방식과 스레드 방식의 성능 비교
- 버퍼 크기별 파일 입출력 성능 비교
- 특정 IP 또는 시간 구간 필터
- 특정 두 호스트 사이의 통신 시간대 조회
- 단일 대형 파일의 안전한 작업 분할

필수 구현을 먼저 완성하고 검증한 뒤 선택 기능을 추가합니다. 실시간 패킷 수집, 웹 대시보드, 머신러닝 기반 이상 탐지, 분산 처리는 기본 범위에 포함하지 않습니다.

## 4. 시스템 구조

```text
사용자: 입력 경로 / 실행 방식 / 스레드 수 / 출력 경로 지정
                           |
                           v
                 [옵션 검증 및 파일 탐색]
                           |
                           v
                    [파일 작업 큐]
                           |
              +------------+------------+
              v            v            v
           [워커 1]     [워커 2]      [워커 N]
           파일 읽기    파일 읽기     파일 읽기
           레코드 해석  레코드 해석   레코드 해석
           로컬 집계    로컬 집계     로컬 집계
              |            |            |
              +------------+------------+
                           v
                     [최종 통계 병합]
                           |
                           v
              [정렬 / Top-K 계산 / CSV 저장]
                           |
                           v
                 [실행 요약 및 성능 기록]
```

### 모듈별 역할

| 모듈 | 역할 |
|---|---|
| `main` | 명령행 인자 해석, 실행 순서 제어, 종료 상태 반환 |
| `file_scan` | 대상 파일 탐색 및 목록 생성, 출력 파일의 재입력 방지 |
| `reader` | `open`, `read`, `close`를 이용한 버퍼 기반 파일 읽기 |
| `parser` | 원본 레코드 해석, 형식 검증, 공통 레코드 생성 |
| `work_queue` | 작업 인출과 큐 상태 관리 |
| `worker` | 파일 처리 및 워커별 통계 유지 |
| `aggregate` | IP별·시간 구간별 집계와 통계 병합 |
| `report` | 정렬, Top-K 선택, CSV 및 요약 출력 |
| `metrics` | 실행 시간, 처리한 레코드 수, 처리량 기록 |

입력 파일 형식에 관한 지식은 `reader`와 `parser`에 모읍니다. 분석 모듈은 공통 레코드만 사용하도록 하여 파일 해석 코드와 분석 로직의 결합을 줄입니다.

## 5. 데이터 처리 설계

### 공통 레코드

원본 데이터를 해석한 뒤 분석에 필요한 정보를 다음과 같은 개념적 구조로 전달합니다. 실제 C 자료형은 데이터 명세에 맞춰 정합니다.

```text
TrafficRecord
  timestamp       패킷 시각
  source_ip       출발지 IP
  destination_ip  목적지 IP
  packet_bytes    통계에 사용할 패킷 길이
```

IP 주소는 원본의 IPv4·IPv6 지원 여부를 확인하여 표현을 결정합니다. 타임스탬프의 단위와 기준 시간대, 패킷 길이가 원본 길이인지 캡처 길이인지는 명세로 고정하고 실행 결과에 기록합니다.

### 파일 입출력

- 파일을 일정 크기의 버퍼로 나누어 읽고, 모든 원본 데이터를 메모리에 올리지 않습니다.
- `read()`가 요청한 크기보다 적게 반환하는 경우와 `EINTR`를 처리합니다.
- 한 레코드가 읽기 버퍼 경계에 걸치면 남은 바이트를 다음 읽기로 이어서 처리합니다.
- 정상적인 파일 끝과 레코드 중간에서 발생한 파일 끝을 구분합니다.
- 길이 정보가 손상되어 다음 레코드 경계를 찾을 수 없다면 해당 파일의 처리를 중단하고 오류로 기록합니다.

### 작업 분배

기본 작업 단위는 파일 하나입니다. 워커는 공유 작업 큐에서 파일을 하나씩 가져와 처리하고, 완료하면 다음 파일을 가져옵니다. 파일 수를 기준으로 고정 분할하는 방식보다 파일 크기 차이에 대응하기 쉽습니다.

입력 데이터가 단일 대형 파일이면 파일 단위 병렬화의 효과가 제한됩니다. 따라서 개발 초기에 파일 수와 크기 분포를 확인합니다. 단일 파일 분할이 필요하면 레코드 경계를 보존하는 별도 설계를 수행하며, 단순 바이트 구간 분할은 사용하지 않습니다.

### 집계 및 병합

- 각 워커는 자체 IP별 해시 테이블과 시간대별 통계를 유지합니다.
- 공유 작업 큐에 접근하는 짧은 구간에 뮤텍스를 사용합니다.
- 패킷마다 전역 통계에 잠금을 거는 대신, 워커 종료 후 로컬 통계를 병합합니다.
- 패킷 수와 바이트 수에는 64비트 카운터를 사용합니다.
- 동일한 IP와 시간 구간의 값을 더하는 방식으로 병합합니다.
- 정렬 값이 같으면 IP 주소 순서 등 고정된 기준을 사용하여 출력 순서를 일정하게 유지합니다.

원본을 버퍼로 읽더라도 IP별 집계 메모리는 고유 IP 수와 워커 수에 따라 증가합니다. 이 구조의 메모리 사용량을 실험에서 확인하고, 메모리 부족은 명시적인 오류로 처리합니다.

## 6. 시스템 검증에 사용할 기본 분석

분석 항목은 병렬 처리와 결과 재현성을 검증할 수 있는 최소 범위로 구성합니다.

| 항목 | 정의 |
|---|---|
| 전체 패킷 수 | 정상적으로 해석한 레코드 수 |
| 전체 바이트 수 | 정상 레코드의 `packet_bytes` 합계 |
| IP별 송신량 | 해당 IP가 출발지인 패킷 수와 바이트 수 |
| IP별 수신량 | 해당 IP가 목적지인 패킷 수와 바이트 수 |
| 시간대별 트래픽 | 지정한 시간 구간별 패킷 수와 바이트 수 |
| Top-K 호스트 | 송신량과 수신량의 합이 큰 IP 순위, 기본 K=10 |

호스트 송수신량의 전체 합은 각 패킷을 출발지와 목적지에서 각각 계산하므로 전체 트래픽의 두 배가 됩니다. 전체 바이트 수는 패킷당 한 번만 더하며, 이를 검증 규칙에 반영합니다.

시간 구간은 타임스탬프와 고정된 기준 시간대로 계산합니다. 서로 다른 날짜의 데이터가 섞여도 같은 시각으로 합쳐지지 않도록 날짜와 시각을 함께 구간 키로 사용합니다.

## 7. 실행 인터페이스와 결과물

다음 명령은 구현 목표를 설명하기 위한 예시이며, 현재 구현된 명령은 아닙니다.

```bash
# 단일 스레드 기준 실행
./traffic_analyzer --input ./data/day1 --mode sequential --output ./results/day1_seq

# 스레드 4개로 동일한 데이터 분석
./traffic_analyzer --input ./data/day1 --mode threaded --workers 4 --output ./results/day1_t4

# 동일 형식의 다른 날짜 데이터 분석
./traffic_analyzer --input ./data/day2 --mode threaded --workers 4 --output ./results/day2_t4
```

| 출력 파일 | 내용 |
|---|---|
| `summary.csv` | 파일 수, 성공·실패 파일 수, 패킷 수, 바이트 수, 오류 수 |
| `hosts.csv` | IP별 송수신 패킷 수와 바이트 수 |
| `timeseries.csv` | 날짜·시간 구간별 패킷 수와 바이트 수 |
| `top_hosts.csv` | 트래픽 상위 K개 호스트 |
| `run_metrics.csv` | 실행 옵션, 처리 시간, 처리량, 입력 규모, 실행 완료 상태 |
| `errors.log` | 실패한 파일 경로, 위치를 확인할 수 있는 정보, 오류 원인 |

다른 실행의 결과가 섞이지 않도록 실행별 출력 디렉터리를 사용합니다. 파일 하나가 실패해도 나머지 파일은 가능한 범위에서 처리하되, 최종 결과에 불완전한 실행임을 표시하고 0이 아닌 종료 상태를 반환합니다. 실패한 파일에서 이미 집계된 정상 레코드도 포함되므로 부분 집계임을 명시합니다.

## 8. 리눅스 시스템 프로그래밍 요소

| 요소 | 적용 목적 | 주요 API 예시 |
|---|---|---|
| 저수준 파일 입출력 | 대용량 데이터의 버퍼 기반 읽기 | `open`, `read`, `close` |
| 디렉터리 처리 | 분석 파일 자동 탐색 | `opendir`, `readdir`, `stat` |
| 스레드 | 여러 파일의 병렬 처리 | `pthread_create`, `pthread_join` |
| 동기화 | 공유 작업 큐 보호 | `pthread_mutex_lock`, `pthread_mutex_unlock` |
| 시간 측정 | 전체 경과 시간 측정 | `clock_gettime(CLOCK_MONOTONIC, ...)` |
| 오류 처리 | 실패 원인 기록과 자원 정리 | `errno`, `strerror` |

초기 버전은 파일 목록이 확정된 작업 큐를 사용하므로 조건 변수 없이 구성할 수 있습니다. 실행 중 작업을 추가하는 생산자·소비자 방식으로 확장할 때 조건 변수를 검토합니다.

## 9. 정확성 검증

### 작은 검증 데이터

손으로 예상 결과를 계산할 수 있는 작은 데이터를 마련하여 패킷 수, 바이트 수, IP별 송수신량, 시간 구간 배정이 맞는지 확인합니다. 원본 형식으로 작은 파일을 만들기 어렵다면 공통 레코드 단계의 검증 입력과 원본 파일 일부를 함께 활용합니다.

### 기준 구현과 비교

동일한 입력에 대해 단일 스레드와 2·4·8개 스레드 실행 결과를 비교합니다. 실행 시간 등 실행별 메타데이터를 제외한 분석 통계가 모두 같아야 합니다. 기준 구현과 병렬 구현이 같은 파서를 사용하므로, 두 결과의 일치만으로 파서의 정확성이 보장되지는 않습니다. 작은 데이터의 예상 결과 검증을 함께 수행합니다.

### 경계 및 오류 상황

- 빈 입력 디렉터리와 빈 파일
- 존재하지 않는 경로와 읽을 수 없는 파일
- 레코드가 버퍼 경계에 걸리는 경우
- 마지막 레코드가 잘린 파일
- 파일 수보다 스레드 수가 많은 경우
- 특정 IP에 집중된 데이터와 고유 IP가 많은 데이터
- 출력 디렉터리를 만들거나 결과를 저장하지 못하는 경우

## 10. 성능 평가

### 비교 조건

- 동일한 입력 데이터와 장비에서 실행합니다.
- 단일 스레드 기준 구현과 병렬 실행의 워커 수 1·2·4·8개를 비교합니다.
- 각 조건을 최소 3회 반복하고 중앙값과 변동 범위를 기록합니다.
- CPU 코어 수, 메모리, 저장장치, 데이터 크기, 파일 수, 컴파일 옵션을 기록합니다.
- 파일 탐색부터 분석 결과 저장 완료까지를 전체 실행 시간으로 정의합니다. 세부 단계 시간은 보조 지표로 측정할 수 있습니다.
- 운영체제 파일 캐시의 영향을 기록합니다. 최초 실행과 반복 실행을 섞어 해석하지 않으며, 기본 실험은 캐시를 강제로 비우지 않습니다.

### 측정 지표

| 지표 | 계산 또는 측정 방법 |
|---|---|
| 전체 실행 시간 | `CLOCK_MONOTONIC` 기준 시작·종료 차이 |
| 레코드 처리량 | 정상 처리한 레코드 수 / 전체 실행 시간 |
| 입력 처리량 | 실제 읽은 입력 바이트 수 / 전체 실행 시간 |
| 속도 향상률 | 단일 스레드 기준 실행 시간 / 병렬 실행 시간 |
| 최대 메모리 사용량 | `/usr/bin/time -v` 등으로 측정 |
| 정확성 | 기준 결과 및 예상 결과와 비교 |

오류 없이 완료한 실행을 기본 성능 비교 대상으로 사용합니다. 스레드 수가 증가해도 디스크 읽기, 작업 편중, 메모리 사용량, 통계 병합 비용 때문에 성능 향상이 제한될 수 있습니다. 특정 배속 달성을 미리 약속하기보다 측정 결과와 병목 원인을 설명하는 것을 목표로 합니다.

5. **실험 근거:** 스레드 수에 따른 시간과 메모리 변화를 측정하고 한계를 설명합니다.
